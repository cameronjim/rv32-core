# Software conventions

How programs for the CPU are built and what they can assume. Fixed in phase 3;
the mmio addresses come from the register map in architecture.md.

## Memory layout (programs/common/link.ld)

| section                          | placement                               |
| -------------------------------- | --------------------------------------- |
| .text                            | imem, VMA 0x0000_0000, 4 KB             |
| .rodata .srodata .data .sdata    | dmem, VMA 0x0000_1000                   |
| .sbss .bss                       | dmem, after data                        |
| stack                            | grows down from __stack_top = 0x0000_1FF0 |
| done word                        | 0x0000_1FFC, reserved, magic 0x0000_600D |

There is no load-time copy of .data: the CPU has no load path from imem, so
initialized data is preloaded directly into dmem. Every program build produces
two hex files, one for imem (.text) and one for dmem (data sections), both
generated by tools/hex_gen.py from objcopy binary output. The simulation
testbench loads both; on hardware both become BRAM initial content.

## Startup (programs/common/crt0.s)

crt0 provides _start at 0x0: set sp to __stack_top, set gp to
__global_pointer$ (with .option norelax around the load), zero .sbss and .bss
(dmem is not zeroed by anything else), call main. If main returns, store the
done magic 0x600D to 0x1FFC and spin forever. Demo programs never return; test
style programs can just return from main and the marker signals completion.

## Compiler and flags

riscv-none-elf-gcc with `-march=rv32i -mabi=ilp32 -nostdlib -ffreestanding
-O2 -Wl,--no-relax -T programs/common/link.ld`. RV32I has no hardware multiply
or divide; `-lgcc` is linked so occasional soft multiply is available, but
demo code prefers shifts and adds. All mmio access goes through the volatile
pointers in programs/common/mmio.h, so -O2 cannot reorder or drop I/O.

## Simulation vs hardware builds

Human-scale delays (an LED blink you can see at 50 MHz) are millions of
cycles, which is far too slow to simulate. Every program takes its delay and
loop constants from programs/common/config.h, which selects small values when
built with -DSIMULATION and real-time values otherwise. The Makefile builds
both flavors: sim hex files land in programs/hex/ and are committed so
`make test` never needs the cross toolchain; hardware hex files are generated
on demand in programs/build/ (gitignored) for the phase 4 Quartus flow.

## Demo programs (programs/)

| program       | behavior                                                        |
| ------------- | --------------------------------------------------------------- |
| led_blink     | walks a lit bit back and forth across LEDR with a delay         |
| counter       | counts up on HEX0..HEX3 in decimal, wraps at 9999               |
| switch_mirror | continuously mirrors SW onto LEDR and its value onto HEX0..HEX2 |
| fibonacci     | computes the sequence, shows each value on the HEX displays, restarts on overflow |
| memtest       | walking-ones and address-pattern test over a dmem window, LEDR shows 0x3FF pass or a failure code |
| reaction      | waits a pseudo random delay (seeded from CYCLE), lights an LED, measures cycles until a KEY press, shows the count on HEX |

Each demo is a single C file in programs/ built by programs/Makefile
(`make -C programs <name>` or `make -C programs all`). The simulation
testbench tb/demo_tb.sv instantiates the core with a behavioral mmio model
(tb/lib/mmio_sim.sv), runs every demo's sim build, drives switch and key
stimulus where relevant, and checks observable mmio behavior per program.
