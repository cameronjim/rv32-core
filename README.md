# rv32-core

rv32-core is a RISC-V RV32I CPU built from scratch in SystemVerilog, synthesized onto the
Cyclone V FPGA on an Intel/Terasic DE1-SoC development board. It is a real processor that
executes real RISC-V machine code on physical hardware. The goal is to understand how a
computer works at the gate level by designing one: datapath, control, memory, I/O, all
written by hand.

This is a learning project by a computer engineering student. It starts as a single-cycle
implementation that can run basic programs, then evolves into a pipelined processor with
hazard handling. The DE1-SoC's onboard peripherals (LEDs, 7-segment displays, switches,
buttons) serve as I/O and real-time debugging tools.

## What this ships

**A single-cycle RV32I CPU.** Implements the full RV32I base integer instruction set
(~40 instructions). One instruction completes per clock cycle. The datapath includes:

- A 32-entry register file (x0 hardwired to zero)
- An ALU supporting all RV32I arithmetic and logic operations
- A program counter with branch/jump logic
- An instruction decoder that maps opcodes to control signals
- A memory interface for instruction fetch and data load/store

This is the foundation. When this works, you can write assembly programs and watch them
execute on hardware.

**Instruction coverage.** All RV32I instruction types:

- R-type: add, sub, and, or, xor, sll, srl, sra, slt, sltu
- I-type: addi, andi, ori, xori, slti, sltiu, slli, srli, srai, lw, lh, lb, lhu, lbu, jalr
- S-type: sw, sh, sb
- B-type: beq, bne, blt, bge, bltu, bgeu
- U-type: lui, auipc
- J-type: jal

**Memory system.** Instruction memory and data memory, initially as on-chip block RAM
(BRAM) inferred from SystemVerilog. Programs are preloaded into instruction memory at
synthesis time (from a hex file generated by the RISC-V toolchain). Data memory is
read/write. Memory is byte-addressable with word-aligned access for lw/sw and support for
halfword and byte loads/stores.

**Memory-mapped I/O.** The DE1-SoC peripherals are accessible to programs running on the
CPU through memory-mapped addresses:

- LEDs (LEDR): write a value, the corresponding LEDs light up
- 7-segment displays: write a value, it appears on the hex displays
- Switches (SW): read the current switch positions
- Buttons (KEY): read button press state

A program running on the CPU can read switches and respond by lighting LEDs or updating
the display. This is the primary way to interact with and demo the CPU.

**A testbench and simulation environment.** Every module has a corresponding testbench.
The CPU can be simulated before synthesizing to hardware. A top-level testbench loads a
program, runs it for N cycles, and checks register and memory state against expected
values. Simulation is the primary debugging tool.

**A 5-stage pipeline (stretch goal).** After the single-cycle version works, refactor into
a classic 5-stage pipeline: Instruction Fetch (IF), Instruction Decode (ID), Execute (EX),
Memory Access (MEM), Write Back (WB). This introduces:

- Pipeline registers between stages
- Data hazard detection and forwarding (bypass MUX from EX/MEM/WB back to ID)
- Load-use hazard detection and stalling (insert bubble when a load result is needed
  immediately)
- Branch hazard handling (flush on misprediction, or static predict-not-taken)

**UART output (stretch goal).** A memory-mapped UART transmitter peripheral so programs
running on the CPU can send text to a serial terminal. Write a character to the UART
address, it gets transmitted over the DE1-SoC's serial interface. This enables printf-style
debugging and demo programs that output text.

**HPS bridge integration (stretch goal).** Use the HPS-to-FPGA bridge so the ARM processor
running Linux can load programs into the RISC-V CPU's instruction memory at runtime,
start/stop/reset the CPU, and read back register state. This turns the DE1-SoC into a
RISC-V development platform without needing to resynthesize for every new program.


## Toolchain

Programs for the CPU are written in RISC-V assembly or C, compiled using the RISC-V GNU
toolchain (`riscv-none-elf-gcc` from the xPack distribution). The output is a flat binary
or hex file that gets loaded into instruction memory. A Makefile target converts ELF
output to the hex format the memory initialization expects.

Simulation runs in Icarus Verilog with GTKWave for waveforms. Synthesis targets Quartus
Prime Lite 23.1std for the Cyclone V (5CSEMA5F31C6). See
[claude-docs/toolchain.md](claude-docs/toolchain.md) for setup details.

## Demo programs to write

These programs run on the CPU you built and serve as both tests and demos:

- LED blink: a loop that shifts a pattern across the LEDs with a delay
- Counter: counts up on the 7-segment displays
- Switch mirror: reads switches, displays their value on LEDs and 7-segs in real time
- Reaction timer: lights a random LED after a delay, measures button response time using
  a cycle counter, displays the result
- Fibonacci: computes the sequence, displays each value on the 7-segs
- Memory test: writes and reads back patterns to verify the data memory works

## Code rules

**SystemVerilog, synthesizable subset only.** No `initial` blocks in synthesizable code
(only in testbenches). No delays (`#10`) in synthesizable code. Everything that hits the
FPGA must be synchronous, clocked logic or purely combinational. Infer block RAM, don't
instantiate vendor primitives unless necessary.

**Quartus project targeting the Cyclone V (5CSEMA5F31C6).** Pin assignments match the
DE1-SoC documentation. Clock is CLOCK_50 (50 MHz). Include the DE1-SoC pin assignment
file (.qsf or .tcl) in the repo.

**Every module gets a testbench.** Testbench files are `*_tb.sv` alongside the source.
Test individual modules (ALU, register file, decoder, memory) in isolation before
integrating. The top-level CPU testbench loads a known program and asserts expected
register/memory values after execution. Simulation must pass before synthesis.

**One module per file.** File name matches module name: `alu.sv` contains `module alu`,
`reg_file.sv` contains `module reg_file`. No multi-module files.

**No file over ~400 lines.** SystemVerilog is denser than C; if a module approaches this
limit, it's doing too much. Split it.

**Naming conventions:**

| Element            | Convention        | Example                              |
| ------------------ | ----------------- | ------------------------------------ |
| Modules            | `snake_case`      | `alu`, `reg_file`, `mem_controller`  |
| Ports/signals      | `snake_case`      | `read_data`, `alu_result`, `pc_next` |
| Parameters         | `SCREAMING_SNAKE` | `DATA_WIDTH`, `ADDR_WIDTH`           |
| Constants/defines  | `SCREAMING_SNAKE` | `OP_ADD`, `ALU_SUB`                  |
| Testbench modules  | `*_tb`            | `alu_tb`, `cpu_top_tb`               |
| Clock              | `clk`             |                                      |
| Active-low reset   | `rst_n`           |                                      |

**Use `logic` not `reg`/`wire`.** SystemVerilog's `logic` type everywhere. Avoid legacy
Verilog `reg` and `wire` distinctions.

**Comments are single-line only.** `//` exclusively. A comment at the top of every `.sv`
file describing the module in one to three lines. Inline comments for non-obvious control
signal assignments, state machine transitions, and hazard handling logic. Never narrate
the obvious.

**Parameterize widths.** Data width, address width, register count as parameters, not
hardcoded magic numbers. Even though RV32I is 32-bit, using parameters keeps the code
readable and documents intent.

**Reset is synchronous and active-low.** Every sequential block checks `rst_n`. On reset,
the PC goes to the reset vector (0x00000000), registers clear to zero, pipeline registers
flush.

**Writing style.** No em dashes. No "utilize" or "leverage." Direct, specific, human prose
in docs, comments, and README.
